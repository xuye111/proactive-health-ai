# 当前架构：痛风随访用户端

## 默认页面与数据流

`HashRouter` 提供首页 `/`、小满 `/agent`、记录 `/record`、我的 `/profile` 四个入口。`/solutions` 返回首页；`/trends`、`/plan` 返回记录；旧知识图谱、记忆与知识路由重定向到我的或安全说明。旧组件代码保留用于原型回归，不经默认路由暴露。

```
记录页的随访任务 → GoutFollowUpPanel → goutFollowUp.ts 状态机 → followUpStore.ts 本机存储
                                                              ↓
                                      首页基线 / 小满对话 / 记录时间线
```

`goutFollowUp.ts` 校验已确认的缓解日、医生安排日、复查进度和报告原始信息；`goutPrompt` 按事项状态与跟进日期生成问句。刚记录发作缓解时，可以先核对医生是否已有安排。用户只能关联本轮报告，提前检查需要确认；仅约复诊直接结束安排核对。首页和记录页用 `isGoutFollowUp` 过滤旧通用健康事项，因此旧睡眠数据不会被解释成痛风数据。安全事项独立优先提示。

小满离线问答由 `goutChat.ts` 负责，先调用 `safety.ts` 的 `redFlagFor`，再查询本机痛风事项或已收录知识。回复可带任务链接，指向 `/record?view=tasks`，有明确事项时附上事项 ID。随访任务也可带事项 ID 返回小满继续问。诊断、报告解释和治疗调整由医生负责。

本机存储延用 `pha.followUps.v1` 与 `pha.health.v2`，保存旧资料以兼容已存在的浏览器数据。新聊天使用独立 key，避免旧睡眠对话出现在当前页。普通提醒在小满对话页显示，页面打开期间每分钟更新本地时间。夜间 22:00–08:00 或用户暂停时隐藏。当前采用应用内提醒。

## 保留的架构原型

`src/ai/agent.ts`、`providers/`、`guardrails.ts` 和通用健康数据组成旧评测流水线，保留了 Provider 接缝、规则降级、Trace 与致命违规整体替换。`npm run eval` 验证的是这条旧流水线，不能代表当前痛风问答准确率。旧睡眠、商城和个人健康判断模块仍有领域回归，未纳入当前默认用户端。真实模型适配器默认关闭。

# AI 架构

> 这一层解决的问题是：**判断逻辑应该长什么样，才能既守得住医疗边界，又能换成模型。**

## 一、分层

用户端 V2 新增独立的本人记录路径：`healthStore.ts` 按日期保存可缺失字段，`healthScore.ts` 计算生活状态分，`personal.ts` 只根据本人同源记录与 `safety.ts` 生成保守观察，`followUps.ts` 管理持续事项。演示流水线仍使用样例档案与 30 天数据；本人模式不读取样例结论。两条判断入口尚未合并到同一个 Trace 流水线，专业服务接入前需要统一上下文与审计。

```
展示层（React 页面 / src/pages）
  只消费视图模型与 Trace，不含任何判断逻辑
        │  useTodayPlan() / useAnswerView()  ← src/ai/hooks.ts（异步会话缓存）
        ▼
编排层（src/ai/agent.ts）—— Health Daily Agent Workflow（方案 §11）
  ① 档案 ② 数据 ③ 个人基线 ④ 结构化信号 ⑤ 记忆召回
  ⑥ 构建 Context ⑦ Provider ⑧ 安全守门 ⑨ 产出行动 ⑩ Trace ⑪ 写记忆（调用方）
        │
        ├─ src/ai/signals.ts        信号识别（纯函数，阈值显式）

        ├─ src/ai/context.ts        Context Builder（方案 §13）
        └─ src/ai/guardrails.ts     守门层（强制、与生成无关）
        │
        ▼
Provider 接缝（src/ai/provider.ts）—— 唯一与「用什么实现判断」相关的地方
        ├─ providers/rules.ts  默认实现，离线可跑，也是降级兜底
        ├─ providers/llm.ts    真实模型适配器（HTTP + 结构化输出校验）
        └─ providers/mock.ts   脚本化假模型（喂越界输出，验证守门层）
                │
                ▼
        src/ai/transport.ts    传输层（fetch 实现 + 脚本化实现）
        src/ai/safety.ts       ★ 安全规则单一来源（生成层与守门层共用）

```

## 二、四条关键设计决策

### 1. 守门层与生成层分离

模型（或规则）**提议**结论，守门层**决定**结论能不能出门。这和「在提示词里写清楚边界」是两种性质的东西：提示词是请求，守门是保证。

守门层不认识 provider，只做八件事：

| 代码 | 致命 | 规则 |
| --- | --- | --- |
| `LEVEL_INVALID` | 否 | 分级必须是四级之一（模型自造的分级会被修正） |
| `RED_FLAG_NOT_ESCALATED` | **是** | 命中急症/越界规则却给了普通建议 → 强制替换为升级文案 |
| `FORBIDDEN_CLAIM` | **是** | 诊断断言 / 用药建议 / 剂量 / 疗效承诺 / 劝阻就医 |
| `MISSING_EVIDENCE` | 是（无依据可用时） | 结论必须带依据，缺失用当日信号补齐 |
| `ACTION_OVERLOAD` | 否 | 单日行动 ≤ 4 条（护栏指标「过度干预率」的结构约束） |
| `MISSING_ACTIONS` | 否 | 日程结论必须有今日行动，否则回落默认计划 |
| `ANSWER_TOO_LONG` | 否 | 回答 ≤ 600 字，按句边界截断 |
| `UNKNOWN_CITATION` | 否 | 引用必须指向存在的知识条目，否则剥离 |

**致命违规的处理是整体替换，不是局部修补**（fail-closed）：被污染的结论里，你无法确定哪一句还安全。医疗场景宁可答「这条我答不了」。

### 2. 安全规则只有一个来源

`safety.ts` 同时被 provider（提前走升级路径）与守门层（拦截不当输出）引用。如果两处各写一份「什么算急症」，迟早漂移——而漂移的代价是漏报。

每条急症规则的文案与依据都指向知识条目里的「需要就医的情况」，所以**知识层 → 规则层 → 守门层**是可追溯的一条线。评测集里 6 条 C 类用例就是这条线的守卫。

### 3. 降级路径：规则实现就是兜底

模型超时、报错、返回非 JSON、结构化校验失败 → 编排层回退到规则 provider，并在 Trace 里记下降级来源。医疗产品不能因为模型服务抖动而失能。

这条路径有专门用例守卫（G-09 provider 抛错、G-10 返回非 JSON），不需要真实 API key 就能验证。

### 4. Trace 是一等公民

每次判断都有 Trace：流水线各阶段耗时、识别到的信号（含阈值）、召回的记忆（含相关性分数与命中原因）、知识引用、守门判定、token 用量、以及是否降级。

它同时服务三个目的：可观测性（出问题能定位）、产品可信度（用户能看见「为什么给这条建议」）、以及指标（`docs/metrics.md` 里的「建议-依据一致率」由此可测）。

界面上就是每条 AI 消息下的「判断过程」面板。

## 三、为什么需要 Provider 接缝

| 能力 | 没有接缝时 | 有接缝时 |
| --- | --- | --- |
| 换模型 | 重写判断逻辑 | 换一个 provider，断言不变 |
| 评测 | 只能测规则 | 两套实现跑同一批断言（`--provider=rules\|llm`） |
| 验证安全 | 依赖真实模型碰运气 | 用脚本化假模型喂越界输出，稳定复现 |
| 降级 | 想不出来怎么降 | 规则实现天然就是兜底 |
| 成本控制 | 不知道贵不贵 | Trace 记 token，可对比 |

## 四、模型接入的现状与边界

- `providers/llm.ts` 是**完整可用的真实适配器**：OpenAI 兼容协议、超时、结构化输出校验、token 统计；
- 它**默认不启用**，`npm run eval` 用规则实现跑基线，因此 CI 不需要任何 API key；
- 在浏览器里直连模型会暴露 key。真实部署应把模型调用放在服务端（BFF），客户端只与本服务通信——`transport` 接缝就是为这个替换预留的；
- 接入前的合规前置动作见 `docs/compliance.md`（单独同意、数据处理协议、字段脱敏）。

## 五、这一层做的事与不做的事

**做**：信号识别、上下文组装、记忆召回、provider 调度与降级、安全强制、可观测性。

**不做**：UI 展示（在 pages）、数据存储（在本机 store）、知识内容本身（在 Markdown 条目）。

## 七、已知不足

1. **没有服务端**：Trace 只在本机内存，刷新即丢；真实部署需要落库以便审计与指标聚合；
2. **记忆召回是关键词级的**：口语表达召回不稳，第三阶段换向量召回，接口不变；
3. **多轮上下文有限**：只支持简短省略式追问承接上一轮问题；
4. **规则关键词仍是人工维护**：接入模型后应改为「模型判定 + 规则兜底」的双保险，而不是直接删掉规则。
