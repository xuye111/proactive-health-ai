# 用户端 V2：持续跟踪与今日状态

> 历史设计档案：此通用健康/睡眠页面已退出默认用户端。当前产品是痛风随访。

状态：用户已同意实施；本机版核心流程已落地，剩余接缝见实施计划
日期：2026-09-26  
范围：现有移动端 PWA 的用户侧；专业服务后台另行设计。

## 1. 目标与边界

用户希望打开应用时看清当天状态、相对自身的变化，以及小满正在跟进什么。每天有新记录或反馈后，页面立即更新；跨天回访要能根据执行和后续状态继续、调整或结束一项行动。

本阶段继续定位为生活方式管理演示。`0–100` 是**今日生活状态分**，只表达已记录的睡眠、活动、主观感受和生活节律与个人目标的符合程度，不是健康风险、疾病概率或临床判断。急症、用药等安全规则保持独立，优先于分数及普通提醒。所有真实医疗服务声明、专业人员工作台、诊疗决策均不在本阶段。

“实时”在本阶段指用户保存记录或反馈后即时重算，以及打开应用时检查应提醒事项；关闭应用后的可靠推送需要服务端，放在后续阶段。先用本机存储，不接模型服务、设备平台或新依赖。用户可选择清除本机记录。

## 2. 用户场景与完成标准

1. **首次打开**：直接进入统一首页；当日模拟设备读数按本机日期展示，并明确标注模拟来源。用户补充记录时只覆盖所填字段。
2. **每日记录**：输入或修改睡眠、活动、主观状态；每项显示日期、来源和最近更新时间。未填项保持缺失，不写成零。
3. **今日状态**：有足够数据时显示可解释的状态分、分项和与近期自己的变化；资料不足时显示“资料不足，暂不评分”及最少还需记录的项目。
4. **主动跟进**：出现持续变化时，小满指出依据并提出一个确认问题；用户可确认、说明不适用或稍后处理。同一事项不重复打扰。
5. **行动与回访**：用户选择一项可执行行动，记录完成、未完成或不适用及原因；约定回访后，比较后续数据和主观感受，并给出继续、调整、结束或建议就医的下一步。
6. **查看历史**：可看近 7/30 天状态分及其分项、已跟进事项与结案原因；趋势含模拟读数时明确标注；用户补充记录的目标达成单独统计。

## 3. 数据与时间

### 3.1 每日记录

沿用 `DailyRecord` 的睡眠、步数、活动分钟、三餐、咖啡因、精力、压力和情绪字段，但用户记录允许字段缺失。新增最小元数据：`date`、`source`（`demo` / `manual`）、`updatedAt`。系统日期取设备当地日期。内置样例按固定日期映射到最近 30 天；个人填写按日期和字段覆盖样例，并保留更新时间及字段来源。

`src/data/healthRecords.json` 作为模拟设备数据源。当前状态分与趋势允许使用模拟读数，但必须标明仅供体验；模拟信号不得生成个人回访事项。真正的个人基线需要真实设备历史或本人记录，不能用模拟历史宣称已建立。需要避免跨零点的睡眠时间归属错误，并为手动录入做合理范围校验。

### 3.2 跟踪事项

一个持续事项包含：稳定 id、关注主题、首次发现时间、触发信号及证据快照、用户确认、当前行动、下次回访日期、状态和按时间排序的事件。状态依次为 `待确认 → 进行中 → 待回访 → 已结束`；安全升级可从任意状态进入 `建议就医`。同一主题未结束时合并新证据，不另开重复事项。用户可以关闭、稍后处理或调整行动。

行动完成状态继续复用现有 `useTodayActions` 的按日存储思路，但要增加“未完成原因”和回访结果；只勾选不代表产生效果。当前页面展示的“评估效果→重新规划”应由这些事件驱动，不再是固定流程标签。

## 4. 今日状态分与变化提醒

### 4.1 分数语义

首版公式是可复核的产品假设，版本号单独记录为 `score-v0.1`；**不宣称医学验证**。总分由三组、七个输入组成：睡眠 40 分（时长 25、入睡规律性 15），活动 30 分（步数 15、活动分钟 15），主观状态 30 分（精力、压力、情绪各 10）。分项先算为 `0–100`，再按上述权重求加权平均并四舍五入。日常节律中的咖啡因与三餐作为提醒上下文，暂不进入分数；体重、家族史、疾病和药物也不参与分数。

`score-v0.1` 的具体映射：睡眠时长相对用户设定目标，每相差 0.5 小时扣 10 分；入睡时点相对有效历史的中位数，每相差 15 分钟扣 10 分（至少 3 天可用记录）；步数相对至少 7 天有效记录的个人中位数计算达成百分比，上限 100；活动分钟相对用户设定的日目标计算达成百分比，上限 100；精力与情绪用 `(值 - 1) × 25`，压力用 `(5 - 值) × 25`。所有分项限制在 `0–100`。这是演示用反馈尺度，不解释为临床阈值；目标和个人基线须在分项详情中可见。当天未结束时活动分标为“进行中”，不把上午的低步数说成全天活动下降。

计算约束：分项必须有数据才参与；至少须有睡眠时长、一个活动输入和两个主观状态输入，且已获得总权重不少于 60%，才计算总分。可计算时将已获得的权重归一化，同时显示覆盖度与“暂定”标记；缺失不当作 0，也不能因只填一项就得到漂亮的高分。修改一项记录后，只更新相关分项与总分；勾选行动只影响计划完成度，不直接加分。分数旁显示“据哪些日期的数据计算”和“数据覆盖情况”。分数历史保留计算版本，公式升级后仍能解释旧结果。

### 4.2 变化与提醒

变化提醒由现有 `src/ai/signals.ts` 的结构化信号扩展而来，直接比较有效记录、个人基线和连续天数；不由总分高低反推。提醒至少包括：发生了什么、比较口径、记录日期、要用户确认的问题、可用动作。优先级为安全升级 > 数据缺失/过期说明 > 待回访事项 > 新的生活方式变化。提醒在应用打开或数据更新时生成，具有稳定 id、去重和冷却期；用户可设置安静时段和暂停非安全提醒。

急症提问照现有安全层处理，不能通过高状态分抵消，也不能被普通提醒覆盖。对样本不足、数据冲突、近期数据过期的情况，显示不确定性及补录建议，不生成确定语气的“状态良好”结论。

## 5. 页面调整

- **首页**：首屏展示今日生活状态分和来源，下面是小满今日观察、健康方案入口、最近 7 天状态变化与持续事项；分项可展开，详细指标留在健康记录。
- **小满**：展示变化和持续事项，接收文字或语音转写；明确数值经用户确认后写入记录。仅在明确产品咨询意图下提示主题，主题不明时先确认；安全和治疗诉求不导向商品。
- **健康方案**：按当前关注主题浏览非药品模拟课程、服务、健康用品和营养食品，支持项目详情、演示金额、下单、模拟付款与本机订单查询；存在就医升级事项时暂停展示和下单。营养食品无资质、标签、适宜人群或功效核验；没有真实供应商、收款或履约能力。
- **我的**：前置健康记录入口，支持个人信息和每日目标编辑；数据与设备只说明来源，本机清除放在次级设置。健康记录的“今天/趋势”保留原有双时间尺度。

静息心率及收缩压、舒张压在模拟设备样例中显示为监测参考，不参与 `score-v0.1`、趋势结论或医学风险判断；个人页不把这些读数设为每日手动填写任务。小满会话可识别用户明确说出的主观量表和咖啡因数值，语音仅负责转写，展示提取结果并确认后才写入。首页聚焦状态与行动，完整读数留在记录页。未来接入设备时应逐项保存测量时间、来源设备、授权状态和单位，再处理不同来源的重复读数。优先评估 Apple HealthKit 与 Android Health Connect 的睡眠、步数、活动、静息心率及血压权限；浏览器 PWA 当前没有这些原生读取能力。两端 HRV 指标定义也不同，不能直接合并为一个趋势。

## 6. 实现顺序与代码边界

1. **数据真实化**：给现有记录派生层一个“日期 + 数据源”的输入，补按日存储与编辑入口；先解除 `today = records.at(-1)` 在真实模式下的隐式假设。
2. **状态分**：把 `insights.json` 中固定的 78 分替换为纯函数计算及可解释分项，`ScoreRing` 继续负责显示。新增针对缺失、越界输入、日期切换和分数更新的验证。
3. **提醒与事项**：复用信号、安全、行动和记忆结构，增加最小事项状态与事件；让“完成/未完成/回访”回流到次日判断。评测覆盖去重、冷却、跨天、急症优先。
4. **页面整合**：只在现有 Home、Record、Agent、Profile 中增加入口与反馈，不重做导航和整体样式。
5. **文档与验收**：同步模型卡、指标和 ADR；`npm run build` 与 `npm run eval` 必过，再检查数据流、刷新保持与日期切换。

判断逻辑继续留在 `src/ai/` 或纯派生函数中；页面只消费结果。仅在记录/事项确实需要独立生命周期时增加小型 store，不引入通用状态框架或外部健康库。现有未提交改动保持原样并纳入回归。

## 7. 后台接缝与暂缓项

本机版先验证用户端完整行为。以后若要关闭应用后可靠推送、跨设备同步和专业人员接手，增加一个最小服务端：账户与授权、加密存储、数据同步、计划回访调度、推送订阅、事项交接和审计记录。此后台应接收与用户端一致的每日记录和事项事件，而不重新发明一套对象。专业人员工作台、知识复核发布及医疗服务责任设计另立阶段。

## 8. 验收场景

- 在真实模式下首次打开，看到今天的空记录及补录提示，不显示 2026-09-19 的 78 分。
- 补录睡眠、活动和主观感受后，分数及分项即时变化；刷新后保持；改掉一项后只重新计算受影响的部分。
- 连续多日出现同一睡眠变化，只建立一个事项；用户选择稍后处理，不会反复弹同一提醒。
- 完成行动后只更新计划进度；回访得到新数据后才判断该行动是否值得继续。
- 数据缺失或过期时不会产生确定的健康结论；急症输入始终走升级路径。
- 模拟数据可驱动状态分与趋势；只把用户明确填写的字段写进本机记录，模拟变化不创建个人回访。
