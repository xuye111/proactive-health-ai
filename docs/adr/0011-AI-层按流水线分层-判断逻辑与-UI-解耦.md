# ADR-0011：AI 层按流水线分层，判断逻辑与 UI 解耦

- 状态：早期通用健康原型已采纳。现行痛风随访见[架构说明](../architecture.md#默认页面与数据流)。
- 日期：2026-09-19
- 相关文件：`src/ai/, src/lib/agentRules.ts`
- 相关文档：[docs/architecture.md](../architecture.md)

## 背景

第一版把判断逻辑和 React 写在一个模块里（`agentRules.ts` 里既有纯规则又有 hook），没有流水线、没有 provider 接缝、没有可观测性。方案 §11–14 写的 Health Daily Agent Workflow、Signal 中间层、Context Builder 在代码里都不存在显式对应物。结果是：换模型要重写逻辑，评测只能测规则函数，出问题无法定位。

## 决策

按流水线分层：信号识别 / 记忆召回 / Context 组装 / Provider 接缝 / 守门层 / 编排 + Trace，全部放在 `src/ai/`。页面只消费视图模型与 Trace。

## 备选方案与代价

**A. 保持单模块，只把函数拆成文件**：改动最小，但「架构」这件事仍然只存在于文档里，且评测无法覆盖流水线行为。
**B. 直接上框架（LangChain 之类）**：看起来更专业，但 4 个知识条目、6 类信号的规模下，框架带来的是抽象成本而不是能力，而且会把「守门层」藏进框架中间件里，反而不利于讲清医疗边界。**代价**：分层后代码量增加约 900 行，且需要自己维护 hook 的异步缓存。

## 什么情况下会推翻

当流水线阶段需要独立部署（例如信号计算放到服务端定时任务）时，按阶段边界拆成服务；分层已经为这个方向划好了线。
