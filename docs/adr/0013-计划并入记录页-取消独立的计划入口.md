# ADR-0013：计划并入记录页，取消独立的计划入口

- 状态：早期通用健康原型已采纳。现行痛风随访见[架构说明](../architecture.md#默认页面与数据流)。
- 日期：2026-09-19
- 相关文件：`src/pages/Record.tsx`、`src/pages/record/TodayPanel.tsx`
- 相关文档：[docs/architecture.md](../architecture.md)

## 背景

方案 §4 设计的底部导航是 5 个入口（首页 / AI / 记录 / 计划 / 我的）。实际使用中暴露出两个问题：

1. **「计划」和「记录」是同一件事的两面。** 用户打开「记录」是想看今天的数据，打开「计划」是想看今天要做什么——但计划必须由数据推导（本周目标 vs 今日实际），分开后用户看不到「计划 vs 实际」这个最有用的对照；
2. **底部导航变成了功能清单。** 五个入口里有两个指向同一份数据的两个视图，用户要在两个地方找同一件事。

## 决策

把「计划」并入「记录」页，形成单页纵向流：**今日行动 → 今日数据 → 本周目标与达成 → 计划闭环**。
本周目标卡里直接给出「今日 X vs 单次/单日目标」的对照与达标状态。

导航因此从 5 个入口减为 4 个（首页 / 小满 / 记录 / 我的）。腾出的位置在下一轮给了「趋势」，
随后趋势又与记录合并为页内「今天 / 趋势」两个分段（见 ADR-0002），最终形态是 4 个一级入口。

## 备选方案与代价

**A. 保持 5 个入口**：更贴近方案原文，计划页也可以做得更细（周视图、目标管理等）。
**代价**：用户需要在两个页面之间来回对照才知道「计划做到了没有」；而健康产品的核心动作恰恰是
「对照计划与实际」——这个对照被页面边界切断了。

**B. 保留独立计划页，但在记录页里也放一份行动清单**：两处都能看到行动。
**代价**：同一份数据出现两个入口、两处可能不一致，是典型的信息架构债。

## 什么情况下会推翻

当计划本身复杂到需要独立的周/月视图（例如引入阶段性训练计划、多次目标调整历史）时，
计划应该重新独立成页——但那时的「计划」已经不是「今天做什么」，而是「一段时间的安排」，与今天的数据不再是同一对象。
